# 一、先算清楚：到底是什么东西会超时？

## 1. 直接复制世界、逐候选推进，不是好起点

TH08 的弹丸池有 1536 个正常槽位，激光池有 256 个槽位。原布局中，Bullet 是 4280 字节，整个 BulletManager 约 6.73 MiB。这还不包括玩家、敌人、ECL 上下文和其他系统。GitHub

假设要评估：

- 1536 发弹；
- 未来 96 帧；
- 256 条候选路线。

逐条路线重算，就有：

次弹丸推进，外加碰撞、脚本和其他更新。

而如果每条候选先完整复制一次 BulletManager，仅这个对象的复制量就约 1.68 GiB。不是说内存复制本身必然不可承受，而是它不应该成为每个在线搜索节点的默认操作。

写时复制也不是万能解法：弹丸位置每帧都变，很多页面很快就会变成每个分支独有。

我们应该尽量共享的是已经计算出来的未来轨迹、不可变程序和不受该候选影响的计算结果，而不只是共享尚未写入的内存页。

## 2. 共享预测以后，碰撞查询仍然可能压垮预算

如果这 1536 发弹在规划时域内确实不受候选动作影响，那么弹丸演化只需：

次。

但如果每条候选路线、每个未来帧，仍然遍历所有弹，那么 3775 万次碰撞查询依然存在。

因此，两个优化缺一不可：

> 预测共享，消除重复推进；空间查询，消除不必要的碰撞检查。

这不是仅凭复杂度公式得出的猜测。后面会给实际微基准，结果非常明显。

# 二、用六类源码机制，逐个判断这套思路有没有价值

这里最重要的是区分：

事件很多，不代表决策分支很多；弹很多，也不代表可控变量很多。

## 类型 A：固定环形弹、直线弹、极坐标加速弹

### 源码提供了什么？

EclRunHigh.inl 中可以配置弹丸变换，然后执行环形等射击指令。对极坐标加速，UpdatePolarAcceleration() 更新角度、速度，再重算速度向量。GitHub+1

在“倍率为 1、没有冻结、只有这个变换生效”等限定条件下，可以把它概括成：

这是用于分析的表达；最终实现仍要保留原版的浮点、计时器和变换终止语义。

### 这里的 insight 是什么？

很多看起来复杂的曲线弹幕，对玩家来说其实是外部给定的时空障碍。

只要确认这批弹在当前时域内没有再次瞄准、没有受动作影响的外部改写，就不需要：

```
候选路线 1：把所有曲线弹算一遍
候选路线 2：再算一遍
候选路线 3：再算一遍
```

而是：

```
曲线弹未来轨迹：只算一次
所有候选路线：查询同一份未来危险区域
```

这类弹幕是第一版最应该拿下的。 它证明的不是“因果搜索很强”，而是更基础、更有价值的一点：

> 源码让我们知道哪些未来可以放心共享，而不是为了稳妥对每条路线重跑整个世界。

### 怎样求解？

上层选择穿哪个缺口、从哪侧绕行；下层把通道还原成合法按键。

一开始没有必要做完整符卡的全局最优解。先做滚动的时空通道搜索，并让规划终点落在一个能继续逃生的位置，而不是只要求“最后一帧没撞”。

## 类型 B：整批自机狙——这是“因果事件”最有力的例子

### 源码里有一个很好的结构

SpawnBulletPattern() 先计算一次 angleToPlayer，再把它传给循环中的 SpawnSingleBullet()。也就是说，某次发射的一批扇形或环形自机狙，共用一次取样得到的角度。GitHub

如果其他发射参数已经固定，这一批弹的变化，可以主要归结为：

不是每发弹各有一个自由选择的未来，而是整批弹受一个取样角控制。

注意，这只是“这批弹的发射结果”上的降维，不代表两条产生同一个角度的玩家路线，在完整游戏状态上也等价。

### 这次还发现了一个会影响架构的细节

ECL 里出现射击指令的时刻，不一定就是实际瞄准的时刻。

代码支持把射击指令缓存到 pendingShotInstruction。之后 Enemy::UpdateShotAndAnm() 根据 shootIntervalTimer，重新调用 DispatchShotInstruction()。还有 SHOOT_NOW 等直接发射路径。GitHub+1

所以事件分析器不能只做：

> 找到 ECL 的 SHOOT 指令，记下它的时间。

它必须跟踪：

> 实际在哪次调用中读取了玩家位置，并由此生成了弹幕。

这也是我现在不建议第一版先写一个庞大的“静态 ECL 自动分析器”的原因。先沿真实执行路径记录发射事件，更可靠。

### 我做了一个小型反例测试

以下参数是我为测试构造的，不是实际符卡参数：

```
玩家初始位置：(192, 352)
发射点：(192, 128)
第 32 tick 发射一颗自机狙
弹速：4
玩家横向速度：2
输入队列延迟：2 tick
```

比较两种策略：

| 策略 | 用“玩家一直不动”预计算弹幕，再检查路线 | 按候选路线重新计算瞄准 |
| --- | --- | --- |
| 提前右移，然后停住 | 判定安全 | 第 88 tick 中弹 |
| 取样附近开始右移，并继续移动 | 判定安全 | 测试时域内安全 |

第一条路线提前移动到 (252,352) 后停住。

固定未来模型仍认为子弹朝 (192,352) 飞，所以认为它安全。但真实的条件预测会瞄准 (252,352)，它就撞了。

这个测试证明了因果预测是必要的；没有证明复杂因果搜索一定便宜。

对这类事件，合理的搜索变量是“取样位置或取样角、取样后的出口”，而不是几秒钟内全部按键组合。

## 类型 C：大量弹丸同时再次自机狙——不是几百个独立决策

UpdateAimedDirectionChange() 会在自己的计时条件满足时，再次读取玩家位置。GitHub

所以，控制自由度主要是这次取样的二维玩家位置，而不是 300 个独立角度。

这才是“因果事件”最值得利用的降维。

但要分清两种复杂度：

决策复杂度可以降到搜索少数候选取样位置。

评估复杂度仍然需要计算这些弹对应的方向、后续轨迹和碰撞。不能因为控制只有二维，就认为评估是常数时间。

### 我会怎样搜索？

先从玩家在取样前的可达区域中，提出少量有代表性的取样位置：例如对应不同出口、不同诱导方向的位置。

每个位置产生一份条件弹幕预测；事件前的公共部分复用，事件后的受影响部分单独计算。

不应该为 300 发弹分别决定“向左诱导还是向右诱导”。这些决定本来就不能独立实现。

### 延迟在这里会放大，而不只是让玩家偏一点

假设瞄准时玩家位置误差为 ε，玩家与某发弹距离为 r，之后该弹飞行距离为 L。在小扰动下，瞄准误差导致的后续位置误差量级为：

例如，作为纯几何示例，取样误差 1 个单位、后续飞行 200 个单位：

- 取样距离 200，后续误差约 1；
- 取样距离 20，后续误差约 10。

近距离再次瞄准，是高敏感事件。

所以规划器不仅应该寻找“标称情况下过得去”的取样位置，还应该偏好对输入时序误差不那么敏感的位置。这比统一给 hurtbox 加一个固定半径更合理。

### 为什么这个例子很重要？

它会直接击败“离我很远的弹暂时不用管”的简单裁剪。

所以，“复杂特殊弹幕”并不自动意味着要增加大量世界分支。有时候只是需要一个准确的、可共享的特殊运动模型。

### 合适的 solution 表示

这里的关键不是发明“专门躲瞬移弹的神秘算法”，而是把错误的连续运动模型，换成正确的分段映射模型。

## 类型 E：铃仙的碰撞开关——应该搜索“什么时候穿过去”

这次进一步看 AdvanceReisenBulletPhase()，可以看到不只是简单开关：它有 type 的多阶段转换，其中会设置透明度插值，而碰撞恢复并不是简单由“开始看得见”来判断。GitHub

这意味着两种视觉直觉都可能不可靠：

> 看起来有弹，所以不能穿。
> 看起来淡了，所以现在安全。

求解器应该使用程序中的实际碰撞生效状态。

## 类型 F：旋转激光——少量几何对象可能比大量弹更决定生死

UpdateNarrowRotatingLaserHitbox() 等回调直接调用玩家的激光判定，角度来自敌人的动画 VM。它们不是只能从普通激光池里发现的对象。GitHub

这说明预测器必须把“直接产生致死判定的回调”纳入模型，不能只导出弹丸数组。

但这类危险一旦拿到了正确的：

```
原点、旋转角、角度演化、尺寸、生效时间
```

每个未来帧的几何查询可以很便宜。

从规划角度看，它往往更适合搜索“保持在哪个角度区间”“何时从一侧跨到另一侧”，而不是让逐帧随机候选反复发现同一堵旋转墙。

这里仍然是：用结构帮助提出候选，用真实碰撞语义检查候选。

# 三、16 毫秒问题：我实际测到了什么？

我写了一个独立 C++ 微基准，使用：

```
1536 个弹丸
96 个预测步
256 条预先给定的候选点序列
```

比较四种实现：

| 实现 | 做法 |
| --- | --- |
| 逐候选重算 | 每条候选重新推进全部弹丸，并全量检查 |
| 共享预测＋全量扫描 | 弹只推进一次，但碰撞仍全量检查 |
| 共享预测＋粗空间索引 | 弹只推进一次，只检查所在空间桶的对象 |
| 再加细粒度占用位图 | 明确为空的小区域直接跳过，否则仍精确检查 |

测试环境是当前 Linux 容器，报告的处理器型号为 AMD EPYC 9V74，GCC 14.2、单线程、-O3。每组预热后测量 15 次。下面是完成整组工作量的中位耗时：

| 合成场景 | 逐候选重算 | 共享＋全扫 | 共享＋粗索引 | 再加占用位图 |
| --- | --- | --- | --- | --- |
| 分散直线弹 | 58.49 ms | 57.59 ms | 4.66 ms | 7.06 ms |
| 分散极坐标加速弹 | 372.06 ms | 58.62 ms | 5.89 ms | 8.40 ms |
| 窄结界映射运动 | 291.12 ms | 60.63 ms | 5.53 ms | 8.02 ms |
| 同一粗桶、但精确不相撞 | 32.82 ms | 22.15 ms | 79.53 ms | 3.72 ms |
| 高度集中、大量相撞 | 145.77 ms | 106.84 ms | 104.07 ms | 108.37 ms |

这些结果都保存在附件里，四种实现会检查每个候选／时间点的碰撞计数是否一致，而不是只比较一个总数。

## 这张表支持三个结论

第一，只有预测共享还不够。

直线弹那一行，从逐候选重算改成共享预测，几乎没有解决问题，因为全量碰撞查询仍然占主要成本。

第二，空间索引能带来数量级改善，但不是恒定时间保证。

“同一粗桶、精确不相撞”的测试里，粗索引比直接扫描还慢。它要遍历很长的桶链，却没有减少检查数量。

这一行尤其有意义：没有碰撞，也就不能靠“撞了马上剪枝”来掩盖退化。

第三，细位图应该按需要使用，而不是永远打开。

它解决了这组粗桶退化，但普通场景中，额外构建成本让整体变慢。

这提示我们的实际数据结构应该能在直接扫描、空间桶、局部细化之间选择，而不是迷信一个统一结构。

## 但这不是“完整 solver 已经只要 5 毫秒”

这个边界必须明确：

测试没有 ECL 解释、敌人生成、伤害、随机数副作用、Windows 状态读取和输入提交，也没有搜索本身。 候选路线是预先给定的。

而且所有合成弹幕都是候选无关的。自机狙等动作相关事件，不能照搬这份共享方式。

此外，测试为了验证结果一致，会继续统计已经发生过碰撞的候选。真实生存搜索会提前剪枝，因此最后一行不等于真实规划器一定需要 100 毫秒。

这些测试支持的是：

> 一个重要几何内核有机会进入几毫秒级，但朴素实现和退化情况都会超预算。

不是完整系统的实时性能证明。

# 四、上一轮设想里，我现在认为最需要修正的地方

## 1. “只有少数因果事件”不能作为默认前提

ECL 有逐帧回调、多个执行上下文，也可以读取玩家状态和其他动态量。不能因为语法上是有限种指令，就认为一个预测窗口里只有少数决策点。GitHub+1

更准确的假设应该是：

> 某些局部片段可以共享大量计算；是否成立，需要识别和验证。

遇到每帧高度耦合的片段，算法不会因为叫“事件搜索”就自动变快。

## 2. “世界不受玩家影响”的范围，比直觉窄

擦弹会改变 subrank，并产生其他副作用；动画指令和部分特效也使用共享 RNG。GitHub+2GitHub+2

所以这两句话不等价：

> 当前这批弹的运动，与玩家无关。

> 整个未来世界，与玩家无关。

前一句可能成立，后一句可能不成立。

一个很重要的优化原则是：

未来随机发射失去共享资格，不代表已经发出的确定性弹丸轨迹也要全部重算。

应该按依赖关系让局部预测失效，而不是一发现 RNG 不同就丢掉所有工作；反过来，也不能明知道 RNG 分支不同，还共享下一轮随机弹。

## 3. 全局空间寻路不能只按 (x,y,t) 合并节点

如果两条路线擦弹、射击命中、形态过渡或随机消耗不同，即使到达同一个位置和时间，也可能面对不同未来。

因此空间网格只能用于组织几何搜索。只有未来相关状态等价的节点，才有资格合并。

第一版最好不要试图自动发现一切状态等价关系。可以先限定模式，显式保留少量分支标签，再逐步扩大共享范围。

## 4. 弹丸生成不是无限集合运算

弹丸池容量、空槽寻找、子弹幕生成都会参与实际执行。AdvanceTransformProgram() 中的子弹幕生成会再次进入发射流程。GitHub

因此，不能把不同候选产生的子弹集合随意拼起来，再认为它等价于原版推进。接近容量限制时，生成成功与否、对象生命周期和更新顺序都需要保留。

紧凑模型要减少无关数据，不是改变对象池语义。

# 五、我现在建议的架构：先做一个能被验证的小系统

我会把它收敛成下面这个形状：

```
离线：真实 ECL／资源分析、参考执行器、特殊机制验证
                         ↓
              可复用的预测模型与路线先验
                         ↓
在线：共享危险预测 → 少量条件分支 → 通道候选 → 有限核验
                         ↓
                带消费时序的输入执行
```

## 1. 第一版不要从“自动编译所有符卡”开始

先手工实现并验证少量机制模型，例如：

```
普通运动与变换
整批自机狙
延时再次瞄准
结界映射
碰撞开关
普通及直接回调激光
```

这不是给每张符卡写路线，而是给已读懂的原版机制提供准确实现。

与此同时，保留参考执行器，做相同初态、相同输入下的对照。

之后再考虑根据 ECL 程序自动组合这些模型、提取依赖。否则第一阶段就会陷入“先写一个完整程序分析框架，才能开始验证算法”的循环。

## 2. 一个预测块必须携带适用条件

我建议至少在概念上保存：

```
预测的时间区间
产生这些危险的实体／控制器
依赖哪些变量和事件
在哪些条件变化时需要失效
输出的危险几何
```

例如：

> 这段曲线弹预测，在变换程序、时间倍率、控制器调用序列不变时有效。

或者：

> 这批弹的事件后预测，仅适用于本次自机狙角度参数。

不是“我算过一次就缓存”，而是“我知道在什么条件下可以复用”。

这比一个全世界哈希更有用。无关得分变化不应该让旧弹轨迹失效；相关控制器变化则必须立即失效。

## 3. 搜索需要两种尺度

较长尺度：选通道、取样位置、过门时机、击破窗口。

较短尺度：选择真实按键，处理窄缝、延迟和偏差。

中间可以用保持若干帧的动作原语减少分支，但接近窄缝、危险恢复或再次瞄准时，需要细化到逐帧输入。

不能固定一个粗动作时长，然后指望它在 Lunatic 的所有局面都够精细。

同时，长尺度终点应对应一个有意义的出口或阶段转换，而不是任意第 96 帧。否则依旧可能“预测期内安全，预测期外立即被封死”。

## 4. 完整执行器主要负责可信度，不能不计成本地塞进在线循环

这是最重要的工程取舍之一。

参考执行器首先用于离线验证和性能测量。在线是否能对少量候选做完整短期推演，取决于实测。

例如，假设为这一步分配 3 毫秒，希望检查 2 条候选、每条 12 帧，那么即使暂不计状态准备成本，也要求：

这是一个明确的准入条件，不是我现在已经测到的性能。

若实际完整推演达不到，就不能把“最后交给完整模拟器检查”当成没有成本的兜底。必须缩小在线核验规模，或者把相应长周期工作前移到离线。

而短期核验通过，也只能说明这段有限时域通过，不能包装成整张符卡的安全证明。

# 六、怎样真正面对输入延迟和截止时间？

## 1. 不能把 16.67 毫秒全部算给 planner

在标称 60 次更新／秒下，一个周期是约 16.67 毫秒。但观测可能发生在周期中间，输入也有自己的采样和交接时刻。

TH08 正常游玩中，玩家更新的优先级在输入记录／交接之前；回放输入则在玩家更新之前装入。前面发现的时序区别，这次仍然能从链优先级和 ReplayManager 对应函数中看到。GitHub+1

## 2. 把计算时间变成显式约束

我会给在线 planner 设置一个低于完整帧周期的计算预算，例如先以 8–10 毫秒作为设计目标。这个数字不是实测保证，而是为了不给其他环节留下零余量。

实际应该复用上一轮尚有效的预测，限制本轮扩展量，而不是每帧重新做整组工作。

## 3. 保留有效方案，但不假装有万能 fallback

planner 应该先保存一条仍然适用的输入后缀，再用剩余预算改善它。到截止时间，就提交当前最好且仍有效的结果。

但这里必须有一个条件：

> 旧方案依赖的世界预测和输入队列仍然成立。

如果因为模型失配、意外延迟或新事件，旧方案已经失效，那么“继续旧路线”不自动安全，“停住”也不自动安全。

系统应该明确区分“有有效方案”与“此时没有安全依据”。否则最终演示可能看似很稳定，实际上只是没把失去保证的时刻记录出来。

## 4. 不把卡临界帧的技巧当作第一版主线

上一轮提到的 focus 与实际人／妖状态分离，仍是值得研究的动作自由度。但靠临界计数维持的脉冲切换，会增加对输入消费时序的要求。

第一版我更倾向于先利用：

提前选位、稳健诱导、提前进入出口、合理击破。

精确到切换边界的技巧，应该在输入链和模型已经可靠之后，再作为可选优化，而不是一开始承担核心生存任务。

# 七、还有一个值得利用的“终点”：阶段转换本身

源码中，生命阈值和某些阶段结束路径不只是切换 ECL，也会改变玩家无敌状态。例如相关路径里可以看到设置计时器和 PLAYER_STATE_INVULNERABLE 的行为。具体哪条路径适用，必须跟实际关卡执行对应。GitHub+1

这给了规划器一个比“再躲 200 帧”更有意义的目标：

> 在还来得及的安全窗口里完成阶段转换，并以有利的位置进入下一阶段。

因此射击和走位不应完全分开。

但是，也不能把击破时刻当成自由输入。它必须由真实射击、子机、伤害、生命阈值等状态产生。在线第一版可以先维持简单射击策略，离线识别少数值得调整的击破窗口，而不是每帧同时全面搜索移动、射击和形态。

这能控制开发复杂度，也能减少在线分支。

# 八、接下来怎样验证，才不会走成无底洞？

我建议把可行性验证分成四道明确的门。

| 阶段 | 要回答的问题 | 必须看到的证据 |
| --- | --- | --- |
| 几何与时序 | 模型是否准确？ | 原版与预测的移动、碰撞、生效帧、输入消费一致 |
| 因果预测 | 换一条路线，未来是否算对？ | 自机狙、再次瞄准、阶段分支的多候选对照 |
| 性能 | 真实工作量能否按时完成？ | 包含观测、ECL、搜索、核验的端到端分布与失约记录 |
| 策略能力 | 提前看见未来是否真的减少死亡？ | 同预算下，固定未来／纯局部方法与条件规划的对比 |

第一批真实关卡测试，不需要覆盖全游戏，但必须选到不同失败模式：

一个主要是确定性曲线弹的片段，一个有明显取样诱导的片段，一个有碰撞恢复或空间映射的片段。

这样能分别检验共享计算、条件预测和特殊语义，而不是只挑一个对算法特别友好的画面。

需要记录的不只是“弹量”和“平均耗时”，还包括：

每个预测窗口里有多少动作相关取样、多少世界分支、多少计算能复用、何处首次失配，以及有多少帧没有有效输入方案。

这几个量会直接决定：后续应该优化内核、增强事件模型，还是增加离线路线先验。

## 我的最终判断

这个方向值得做，但“因果事件”本身不是一个把复杂度变没的魔法。

经过这次检查，我认为真正站得住的核心是：

> 把弹幕程序产生的大量重复演化共享起来；把真正受玩家影响的部分参数化；再用通道结构压缩路线搜索。

源码已经给出了很具体的支持：整批共享取样、同时再次瞄准、确定性空间映射、明确的碰撞状态机和阶段转换。它也揭示了不能忽略的反例：延迟发射、共享随机数、副作用和对象池语义。

所以我对两个版本的判断不同：

“每帧从完整世界出发，全面分叉、自动求解未来几秒”——目前证据不足，不应该作为默认设计。

“针对 TH08，离线理解规则与阶段，在线共享预测、只展开少数条件分支，并严格限制计算预算”——有明确的结构依据，也有几何内核的初步性能证据，值得推进。

本次测试的源码、结果和复现说明在这里：。它包含可在 Windows 重新编译的独立 C++ 测试，但当前给出的耗时都是本次容器测量，不是 Windows 原版成绩。

下一步最关键的不是继续扩展架构，而是让上述三类真实片段同时通过“预测正确、按时完成、确实更容易活下来”这三项检查。那才足以把这个想法从合理推断推进到可靠工程。

# 三、莉格露：这次确实找到了“共享主体＋模式选择”的具体例子

## 1. 主体发射块可以预编译，而不是每条路线重新解释

实际符卡是：

灯符「ファイヤフライフェノメノン」

对应 ecldata1.ecl 的主程序 sub38，其中调用的 sub40、sub41 是很好的共享计算对象。

Lunatic 的 sub40 每轮有四次发射请求：

每 9 tick 一轮，共 40 轮。

我直接执行了这个真实字节码的受限发射片段，得到：

| 项目 | 结果 |
| --- | --- |
| 返回时刻 | 第 360 tick |
| 发射轮数 | 40 |
| 发射命令数 | 160 |
| 请求生成的弹数 | 840 |
| 执行的有效 ECL 指令数 | 446 |
| 该片段直接读取玩家或随机操作数 | 0 |

sub41 也得到 840 发请求，但部分角度递推、速度和变换配置不同，不能当成完全相同的模板。

依据：ecldata1.ecl / sub40 @0x639c、sub41 @0x674c；受限执行记录 emitter_slice_results.json。

这里的“840”是请求量，不是屏幕同时存在 840 发；完整游戏还会受到发射门槛、弹池、清除和阶段结束等影响。

**算法上，这种块应该提前编译成发射事件序列。**只要发射原点、时间状态和相关外部条件一致，就让所有候选路线共享相同的主体弹幕演化。

这不是说整张符卡不依赖玩家，而是说：这一块不值得对每条候选重复执行。

## 2. 同一张符卡的使魔，形态选择会明显改变弹量

主程序生成的使魔 sub43 会启动 sub42。

sub42 使用了两组不同的指令掩码：

```
0x3f：对应人类侧条件
0x5f：对应妖怪侧条件
```

结合源码的 Lunatic 与实际人／妖对齐掩码，稳定状态下：

| 使魔所对应的实际形态 | 发射节奏 | 120 tick 请求量 |
| --- | --- | --- |
| 人类 | 每 20 tick，5 发 | 30 |
| 妖怪 | 每 40 tick，2 发 | 6 |

这也是直接执行同一个真实 ECL 发射片段得到的结果。

依据：ecldata1.ecl / sub42 / 0x6bec–0x6c90；sub43 / 0x6d78；源码 Enemy::UpdateYoukaiAlignment() 和 ECL 掩码判断。

对这个发射器而言，妖怪侧请求量减少了 80%。

但这里不能跳到“全程按住 Shift 最好”。切换还影响射击、子机、使魔交互；focusMode 和 isYoukai 又有过渡时间。这个结果应该成为规划器可利用的局部事实，而不是通用口诀。

这一张的合理结构是：

> 主体弹幕共享预测；使魔存活、实际形态与过渡计数进入条件状态；下层规划走位。

这比单纯提高躲弹反应速度有实质优势。

# 四、铃仙：实际资源给出了可以利用的碰撞窗口，而且视觉会误导

具体是：

散符「真実の月（インビジブルフルムーン）」

对应 ecldata5.ecl / sub75。

这次不只是看到了源码里的“碰撞开关函数”，而是把真实调用时刻、标记、弹型和动画初始状态对上了。

## 1. 实际状态机

这批环弹使用 bullet type16，对应 etama.anm 的 script111。

该动画脚本在初始时刻明确设置：

```
type = 1
```

主 ECL 对两种标记弹分别在局部时刻 140、220、240 调用 AdvanceReisenBulletPhase。

对当时存活、标记匹配且处于相应状态的弹：

| 局部时刻 | 状态变化 | 碰撞 |
| --- | --- | --- |
| 140 | type 1 → 0，变透明，速度改为约 0.3 | 关闭 |
| 220 | type 0 → 2，启动 15 tick 的显形插值 | 仍关闭 |
| 240 | type 2 → 1，恢复原速度 | 恢复 |

所以，这些弹的碰撞关闭窗口是局部：

也就是 100 tick。

开始显形，不等于已经恢复碰撞；关闭碰撞，也不等于弹丸停止运动。

依据：ecldata5.ecl / sub75 / 0x84dc–0x85cc；etama.anm / script111 @0x75c84；源码 EclExIns.cpp:669–717。

## 2. 发射量也能明确读出来

主环弹每个父程序循环包含：

发请求。父程序在 t=300 跳回局部 t=90，对应 210 tick 的循环。

但是，t=280 还会生成 16 个使魔，制造其他类型的弹。不能因为主环弹暂时不致命，就把整个画面判为安全。

依据：ecldata5.ecl / sub75 / 0x83a0–0x87cc。

## 3. 一个会让模拟器慢慢失步的参数细节

这个脚本里有两层速度参数：

```
speed1 = 1.4
speed2 = 0.8
count2 = 2
```

很容易把两层实现为 1.4、0.8。但原版的分层公式是：

分母是 count2，不是 count2-1。

因此两层实际是：

```
1.4、1.1
```

另一组 1.2、0.6、2，实际则是：

```
1.2、0.9
```

依据：BulletManager::SpawnSingleBullet()，结合 sub75 的实际参数。

### 对应的 solution 应该怎样求？

这不是“看到透明就穿”。

应该先求：

> 在 t=240 恢复碰撞时，哪些区域是可存活、并且还能继续逃生的？

再往前求：

> 从现在的位置，能否利用关闭窗口进入那些区域？

也就是一个明确的带时间窗口的穿越问题。

它非常适合前向可达性与后向出口约束结合，而不是当前最近弹距离最大化。

# 五、Double Spark：源码函数名字不等于这次具体弹幕的行为

具体是：

恋心「ダブルスパーク」

对应 ecldata4b.ecl / sub55。

## 1. 首轮和后续轮不是同一种取样

Lunatic 首轮的两条方向，是固定角度：

后续循环轮才读取 ANGLE_TO_PLAYER，再分别偏移：

所以不能用一个“每次都自机狙”的模型统一处理。

依据：ecldata4b.ecl / sub55 / 首轮 t150、循环轮 t610。

## 2. 每侧四个 actor，不代表四条独立致死激光

每侧会生成 sub57–60 四个 actor，但实际直接激光判定由 sub57 安装 EX9 完成。

sub57 的局部时序是：

```
t=120：安装逐帧致死判定
t=310：解除
t=370：结束
```

其对应的 stg4benm.anm / script6 中，没有旋转、角速度或旋转插值指令；这个 actor 的 ECL 设置初始角度后，也没有继续改变它。

因此，虽然源码函数叫 UpdateNarrowRotatingLaserHitbox，在这次具体使用中，核心可以按固定方向危险带处理。

依据：ecldata4b.ecl / sub57 @0x86e4；stg4benm.anm / script6 @0x20778；EclExIns.cpp:529–547。

这是有 dat 之后非常实用的区别：

> 引擎支持旋转，不代表每次调用都在旋转。
> 图形 actor 很多，不代表控制自由度和致死几何也一样多。

## 3. 实际求解变量很清楚

对后续轮，可以搜索：

在取样时处于什么位置，让这两条危险带指向有利方向；然后在真正生效前，从哪个出口离开。

但还要叠加 child sub56 的随机相位环弹。这个子程序每 24 tick 发出两组 15 发；受限执行 144 tick 得到 180 发请求。不能只解决大激光，忽略背景弹。

还有一个必须保留的时钟细节：父程序调用的 sub74 会花 32 个 tick 产生特效。CALL 返回时恢复父上下文，所以父程序里的 t=150 不能直接视为从入口起的第 150 个全局帧。子 actor 出生时还会立即执行一次 ECL，也需要与原版更新顺序对齐。

这里真正便宜的是：两条结构清楚的危险带，加一个共享或条件化的环弹背景，而不是对所有画面对象逐个盲搜。

# 六、博丽弹幕结界：既有可共享的复杂几何，也有不能遗漏的玩家分支

具体是：

大結界「博麗弾幕結界」

对应 ecldata4a.ecl / sub46。

这次实际脚本调用的是：

```
EX6：启动宽结界
EX7：每帧更新宽结界映射
```

不是之前举例时分析的窄结界。

## 1. 真实映射参数不同

宽结界的中心是：

跨区时反转速度，并围绕该中心缩放位置。外扩倍率约 1.649916，内缩约 0.606092，不是简单的两倍／一半。

源码还有一个容易被“整理代码”误改的细节：当前区域和上一位置区域判断，左边界分别用了 -32 和约 -31.100006。我们必须保留这个不对称，而不能为了看起来合理而修正它。

依据：ecldata4a.ecl / sub46 / 0x81dc、0x81f0；EclExIns.cpp:354–437。

这套映射虽然视觉复杂，但在控制器状态固定时，不会因为某条候选路线向左、另一条向右，就自动需要计算两遍。

已有弹的这部分演化可以共享。

## 2. 实际发射结构

主体生成 sub47、sub48 各四个使魔。其发射子程序 sub49、sub50，分别每 5 tick 请求 2 发、3 发。

在八个发射器都存活、已进入循环且允许发射时，主体合计：

发／5 tick。

另外还有延迟启动的随机角发射器，必须单独记录其随机依赖。

## 3. 真正会改变候选未来的是这个条件

主程序 0x84e8 的意思是：

```
自机距离 Boss >= 64：
    跳过追加发射

否则：
    发射额外的 5 枚自机狙
```

依据：ecldata4a.ecl / sub46 / 0x84e8–0x8504。

这和“贴近敌人，让它停止射击”的通用距离抑制，方向恰好相反。

因此不能写一个通用规则：

> 有源码，发现距离门槛，所以靠近就能少弹。

正确做法是把具体条件编译出来。这里应比较：在门槛判定发生时，留在 64 之外是否更有利；进入近处得到的输出，是否值得多生成这一轮自机狙。

这张的结构可以写成：

> 共享的结界映射和主体发射器＋随机相位背景＋一个距离条件分支。

这比“整张符卡固定”准确，也比“每条候选重跑全部弹丸”便宜。

# 七、两个真正的压力测试：它们证明不能只做稀疏事件搜索

## 1. Rising Game：贴近后，不只是少一发弹，后续随机世界也可能变了

具体是：

蘇生「ライジングゲーム」

对应 ecldata6.ecl / sub56。

它的一部分其实很好处理：child sub57、58、59 分别每 12、8、5 tick 请求 6、5、9 发环弹。120 tick 合计：

这些子程序只在开始读取一次随机相位，随后按各自角度递推。

但另一部分完全不同。

### 真正复杂的是 sub62 的递归扩散

sub60 会朝自机方向移动，并在自己的局部 60、120、180 生成 sub62。

sub62 做的是：

```
设置最小发射距离 48
请求一枚零速弹，角度仍取随机数
深度计数 +1
达到 9：终止
否则，到局部 t=4：
    选择两个不同、非立即回头的六边形方向
    分别在 24 单位外生成新的 sub62
```

从计数器 0、所有生成都成功等理想条件出发，累计节点数可以是：

这是累计理想节点数，不是同时存在 511 个敌人，也不是实测屏幕有 511 发弹。

依据：ecldata6.ecl / sub60、sub62 @0x7afc。

### 更微妙的因果关系

在源码中，距离门槛是在解析发射角度之前检查的。

所以当自机进入 48 以内：

```
跳过这次发射
    ↓
也跳过这次随机角取数
    ↓
后面选择六边形扩散方向时
使用的随机状态可能不同
```

也就是说：

> “先算好一棵随机扩散树，再把自机附近的弹删掉”不是正确模拟。

而且距离抑制只让 DispatchShotInstruction() 返回，并不会终止后续递归 ECL。

依据：EclDependencies.cpp:697–742，结合 sub62 / 0x7b8c 的随机角操作数和后续随机分支。

### 该怎么求？

我更倾向于优先控制携带扩散种子的使魔走向，以及种子在哪里生成，把复杂扩散引向不妨碍后续逃生的位置。

真的要利用 48 距离门槛时，就必须把 RNG 相位纳入条件推演，而不是几何删弹。

已有确定的环弹仍然共享；扩散链相关的部分才分支。这个例子很适合检验架构是否真正理解因果关系，不适合拿来证明“事件很少，所以很容易”。

## 2. 蓬莱玉枝：一次发射之后，还会有异步的再次自机狙

具体是：

神宝「蓬莱の玉の枝 —夢色の郷—」

对应 ecldata7.ecl / sub71、sub72。

主程序创建七个使魔。在它们都存活到发射的条件下，首轮每个请求 48 发，共：

发。

关键变换是：

```
遇到边界事件
    ↓
结束边界变换
    ↓
重新瞄准当时的自机
```

依据：sub72 / 0xb83c、0xb864、0xb92c；Bullet::AdvanceTransformProgram()、UpdateBoundaryBounce()、UpdateAimedDirectionChange()。

### 两个特别容易读错的地方

第一，配置中的 bounceLimit=0 不等于完全不反弹。

原版先处理边界事件、增加完成次数，再检查限制。因此这里会先处理一次边界事件，再结束该变换。

第二，配置了变换记录，也不代表它会执行。

这里还配置了 SET_SPRITE，但本轮发射的 flags 为 0xa82，不包含 0x4000。因此这个换图记录会被跳过。

这说明 solver 不能仅仅扫描“设置了哪些变换”，还要执行真实的变换程序＋启用掩码＋活动状态。

### 为什么它挑战稀疏事件模型？

不同弹的位置和角度不同，到边界的时刻不同，之后分别读取各自那个时刻的玩家位置。

所以它不是：

> 336 发弹只需要选择一个共同瞄准点。

更合适的处理是：

> 对已经观测到的这批弹，先共享第一次再瞄准前的飞行；把再瞄准按未来更新时间分桶；到相应事件才计算依赖候选玩家位置的后续部分。

远期不能对所有事件组合无限分支。需要离线得到的走位区域、有限动作原语和滚动更新。

这张符卡是我不会在没有原版端到端测试前，轻易承诺“16ms 肯定够”的具体原因。

# 八、有了这些实际结构，算法可以比“共享轨迹＋网格”再聪明一点

我现在认为至少有两种优化值得成为核心，而不是后期补丁。

## 1. 以“弹幕批次”查询碰撞，而不是总以“单颗弹”查询

铃仙这些实际环弹，以及其他多个发射器，都包含均匀角度排列。

对于结构尚未被独立变换、清除等操作打破的一组弹，可以表示为：

查询某个玩家候选位置时，可以先判断它是否接近这圈的半径；再根据角度区间，直接找出可能相撞的几个编号，最后才做原版矩形碰撞。

不必每次都扫描整圈 144 发。

这里的圆和角度只是快速预筛选。最终仍然检查原版的矩形判定，且要处理 float32 逐帧累加误差、被清除的个体、独立变换和退化位置。

一旦结构被打破，就拆分批次或退回单弹查询。不是强行把所有弹幕近似成圆。

## 2. 把候选相关性分成不同数学类型

实际资源已经说明，“读了玩家”不能直接等同于“重新模拟整个世界”。

| 程序结构 | 适合的计算方式 | 本次实际例子 |
| --- | --- | --- |
| 没有候选相关读取 | 预编译、共享演化 | 莉格露主体发射块 |
| 连续但低维的依赖 | 状态递推、批量候选计算 | 一面 sub0 追踪滤波 |
| 少量参数取样 | 在取样参数上分支 | Double Spark 后续轮 |
| 明确状态窗口 | 时空通道与恢复时刻约束 | 铃仙真实之月 |
| 固定空间映射 | 共享特殊运动算子 | 宽结界 |
| 条件改变随机消耗或实体生成 | 保留相关世界状态，局部分支 | Rising Game |
| 大量异步重新取样 | 事件日历、有限时域、滚动修正 | 蓬莱玉枝 |

同一张符卡可以同时由多行组成。

这比“为每张符卡指定一种算法”更合适，也比“全游戏用同一棵事件搜索树”更稳妥。

# 九、关于 16ms：这次有一个真实资源微基准，但它的意义必须限制清楚

我用 C++ 执行了莉格露 sub40 的真实标量指令，生成整个 360 tick 的发射调度。

其结果与 Python 的 160 条有序发射记录哈希一致。

本次容器环境为 Linux x86-64、Intel Xeon Platinum 8573C、GCC 14.2、单线程 -O3。41 批，每批执行 1,000 次，得到：

| 指标 | 完整一次发射调度 |
| --- | --- |
| 中位批次均摊耗时 | 约 5.24 微秒 |
| 批次均摊 P95 | 约 6.18 微秒 |
| 最大批次均摊 | 约 7.87 微秒 |

依据：实验包 native_emitter_benchmark.json 与 bench_real_emitter.cpp。

这没有弹丸运动、碰撞、路线搜索、完整敌人逻辑、状态复制或 Windows 输入。分位数也是批次均摊分位数，不是逐帧尾延迟。

因此，这个实验支持的结论只有：

> 至少对这类真实发射块，解读和生成发射调度本身可以非常便宜，值得提前编译和复用。

它不能证明完整 agent 的 16ms 预算已经解决。

真正要控制的是：

尤其要盯住后三种退化：候选世界分支过多、空间查询失去区分能力、在错误的阶段反复复制和推进大量状态。

我不会让在线算法默认“每帧重新求解未来几秒”。更合理的是：复用仍然有效的预测和方案，给本轮新展开的事件、候选和时域设定硬预算，并在截止时刻提交当前仍适用的结果。

但旧方案的条件已经失效时，继续旧路线或停住，都不能冒充安全保证。

# 十、根据这次结果，我会怎样收敛架构

## 1. 离线做的是“程序特化”，不只是保存固定按键

根据实际 ECL 和资源，为每个阶段生成：

```
必要状态
发射与变换模板
玩家依赖的数学类型
事件与判定门槛
碰撞生效窗口
预测缓存的失效条件
可用的入口、出口和走位原语
```

没有识别出的指令和回调，不能默认忽略。它应阻止相应优化，或回退到参考执行器。

专用的是准确的 TH08 语义；可以复用的是结构分析、规划与控制方法。

## 2. 在线同时运行几种计算方式

已经发出的确定性弹幕共享预测；二维追踪直接递推；自机狙和形态选择只展开必要参数；强耦合扩散保留 RNG 和生命周期状态，在相关时域内有限推演。

下层则分开处理：

选哪条通道、哪个取样区域、哪个过门时机，以及如何用真实按键精确执行。

不能只看当前离弹多远，也不能仅凭两个候选到达同一个 (x,y,t) 就把它们合并。如果它们改变了不同的 RNG、形态、伤害或实体生命周期，后续世界可能不同。

## 3. 延迟模型要使用实际机体参数

SHT 已经给出了真实数据。例如四组组队配置的正常／低速轴向速度为：

| 组队配置索引 | 正常速度 | 低速速度 | hurtbox 满宽 |
| --- | --- | --- | --- |
| 00 | 4.0 | 2.0 | 1.65 |
| 01 | 5.0 | 2.2 | 2.0 |
| 02 | 4.0 | 2.3 | 2.0 |
| 03 | 5.0 | 1.9 | 2.0 |

斜向速度也应直接使用资源值。这里的 1.65 是资源中的满宽，源码会除以二作为 half-size，不是半径 1.65。

依据：8 个 .sht 的解析结果、Player.cpp 的机体文件映射和 hurtbox 初始化。

输入模型仍需包含已经不可撤销的输入队列。正常游玩与 replay 的交接顺序不同；不能在 Player 更新前直接替换按键，再把那种结果当成正常设备输入的延迟能力。

而且，新增实体在出生时会立即执行 ECL，后续对象池遍历还可能在同一游戏更新中再次推进它。这种源码级时序，比估算“我的程序差不多延迟两帧”更值得先核准。

## 4. 第一版应按能区分问题的顺序验证

我会先拿一面追踪小妖、莉格露发射块与形态分支，验证连续依赖、共享计算和实际输入时序。

接着用铃仙真实之月验证碰撞窗口和恢复前出口规划；再加入 Double Spark 和宽结界。

最后用 Rising Game、蓬莱玉枝做强耦合压力测试。

每一步都同时检查三件事：

换了动作，未来是否预测正确；整条链是否按时完成；同样预算下是否确实更容易生存。

不能只挑一个弹幕看起来很密、但算法刚好特别擅长的片段做演示。

## 最终判断

有了 dat 后，这个想法的依据明显比之前强了；但理由不是“原来所有弹幕都很简单”。

恰恰相反，实际脚本告诉我们：

有的复杂弹幕只是可共享的固定计算；有的持续追踪可以降成两个状态；有的模式选择能直接减少大量发射；有的碰撞窗口适合提前穿越；也有的合法操作会连随机世界一起改变。

所以我现在最支持的架构，不是：

> 每张符卡识别几个事件，然后用统一搜索树解决。

而是：

> 把 TH08 的实际弹幕程序，逐段编译成适合计算和控制的模型；共享不变的世界，只对真正变化的部分付出搜索成本。

这是一条有具体数据支撑、值得实现的路线。至于全程 Lunatic NMNB 能否稳定落进 Windows 实时预算，接下来必须由完整状态转移对照和端到端运行来证明，不能由这些局部结果替它背书。
